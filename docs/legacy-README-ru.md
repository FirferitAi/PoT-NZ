# PoT-NZ — Power-of-Two Quantization without Zero

QAT текстовой модели на сетке `k·n/2^p` **без нуля** (теория шага с пропуском нуля).
Полное описание теории — `ТЕОРИЯ PoT-NZ.txt`.

Реализация теории **«шаг с пропуском нуля»** (`ТЕОРИЯ ШАГА С ПРОПУСКОМ НУЛЯ`) на
маленькой текстовой модели: char-level Transformer, обучение с квантованием
(QAT) на каждом шаге.

Проверяются две гипотезы:

* **H1 — работоспособность.** QAT с равномерной сеткой `k·n/2^p` **без нуля** не
  ломает обучение: perplexity сравнима с fp32-базой (порог ≤ 1.1×).
* **H2 — эффективность.** Модель компактнее при том же качестве: ровно `2^(p+1)`
  значений → `p+1` бит без «мёртвого» кода, ноль отсутствует, шаг —
  двоичная дробь (точное представление, никаких 1/3).

Этап 1 — обучение и проверка качества (H1, H2). Этап 2 — **упаковка бит**
(`src/pack.py`, реальный `.bin` и его размер) и серия прогонов p = 5…8, чтобы
найти, где качество упирается в потолок fp32 (см. `runs/report_bits.md`).
Ноль по-прежнему не вырезается — это следующий этап.

## Как теория отображена в код

| Теория | Код |
|---|---|
| шаг `n / 2^p` | `StepQuantizer.step`, `_k_from_u` |
| сетка `k ∈ {-2^p..-1, 1..2^p}`, ноль отсутствует | `skip_zero=True`, округление в 0 → `sign(u)·1` |
| `2^(p+1)` значений, ровно `p+1` бит | `bits_per_weight`, тест `test_levels_count` |
| кодирование `c = k+2^p` (k<0), `c = k+2^p-1` (k>0) | `encode_k` / `decode_c`, `deploy_codes.npz` |
| точные двоичные дроби, без 1/3 | `test_step_is_exact_binary_fraction` (знаменатель шага — степень двойки) |
| QAT через STE | `StepQuantizer.forward` = `w + (q - w).detach()` |
| масштаб на блок (веса не в `[-n,n]`) | `scale_mode: per_block`, `block_size: 32` → +0.5 бита на вес |
| вариант Б: с нулём + вырезание | `skip_zero=False`, доля нулей `zero_frac` в `diag.jsonl` |

Квантуются только `nn.Linear` внутри attention и FFN (`qkv`, `proj`, `fc1`, `fc2`).
Эмбеддинги, LayerNorm, bias и `lm_head` остаются fp32 — как требует план.

## Метрики и диагностика

Каждый прогон пишет в `runs/<имя>/`:

* `train_log.csv` — loss/градиент/lr по шагам;
* `epoch_log.csv` — train loss, val loss, val perplexity по эпохам;
* `diag.jsonl` — доля весов **на сетке**, доля **нулей**, доля **клипа** (|k| = 2^p),
  `mean|k|`, гистограмма `k`, норма STE-градиента;
* `k_hist.png` — гистограмма `k` после обучения;
* `ckpt_best.pt`, `ckpt_last.pt`, `tokenizer.json`, `run.json`;
* `eval.json`, `deploy_codes.npz`, `deploy_meta.json` (после `evaluate.py`);
* `weights_packed.bin` — реальный упакованный файл модели;
* `runs/comparison.md` и `runs/curves.png` — сводка по всей серии.

Размер считается двумя способами: теоретически (`(p+1) + 16/block_size` бит на вес,
остальные параметры fp32) и «файлом без упаковки» (1 байт на код + fp16-масштабы) —
это верхняя граница, упаковка бит в план этого этапа не входит.

## Упаковка бит (`src/pack.py`)

Коды варианта C занимают ровно `p+1` бит и лежат в потоке подряд, без выравнивания
на байт: 8 кодов при p = 4 (5 бит) = 40 бит = **ровно 5 байт**.

```python
from pack import pack_weights, unpack_weights
blob = pack_weights(codes, 5)              # bytes, len = ceil(n*5/8)
codes2 = unpack_weights(blob, len(codes), 5)  # побитово те же коды
```

`pack_model(model, path)` собирает готовый файл:

```
"SZP1" | uint32 (длина JSON) | JSON-заголовок | payload
payload: коды (p+1 бит) + масштабы блоков (fp16) + fp32 для эмбеддингов,
         LayerNorm, bias и lm_head
```

Проверка — `python src/verify_pack.py runs/C_p4_skipzero`:

```
бит на код: 5
слоёв: 16, распаковано без потерь: 16/16
коды: 786,432 байт (uint8) -> 491,520 байт (плотный поток), экономия 1.60×
веса: восстановлено побитово 16/16 слоёв при fp32-масштабах
      (fp16-масштаб даёт расхождение 6.1e-05 на весах)
perplexity: исходная 7.819, из .bin 7.819 (разница 0.001%)
```

Размеры p = 4 (fp32-модель 3 305 472 байт):

| вариант | байт | сжатие |
|---|---|---|
| коды без упаковки (1 байт/вес) | 995 328 | 3.32× |
| теория (p+1 бит + fp16-масштабы) | 700 416 | 4.72× |
| **реальный `.bin` (fp16-масштабы)** | **707 183** | **4.67×** |
| реальный `.bin` (fp32-масштабы) | 756 335 | 4.37× |

Разница с теорией — только JSON-заголовок (6759 байт на 53 тензора).
Масштабы хранятся по одному на блок из 32 весов (16 бит / 32 = 0.5 бита на вес);
режим fp32 даёт побитово точные веса, но стоит ещё 0.5 бита на вес.

### Разреженная упаковка (SZM1)

Для варианта B (сетка с нулём) есть формат с битовой маской:

```
"SZM1" | JSON | маска нулей (1 бит на вес) | коды ненулевых (p+1 бит) | масштабы (fp16)
```

`pack_sparse` / `unpack_sparse` в `src/pack.py`, проверка — `python src/verify_sparse.py runs/B_p4_zero`.
На реальной модели (`B_p4_zero`, 5.83% нулей) выходит:

| | байт |
|---|---|
| плотный `.bin` (6 бит на все веса) | 805 489 |
| разреженный `.bin` (1 бит маски + 5 бит) | 777 600 (**−3.46%**) |
| для сравнения: 5-битная сетка без нуля, та же архитектура | 707 183 |

Нули встают на место побитово (`16/16` слоёв, 45 811 нулей), ppl не меняется.
Порог окупаемости на реальном файле: **f > 20%** против 5-битной сетки
(или любая ненулевая доля против плотного 6-битного B). При f = 5.83% вырезание
нуля по-прежнему невыгодно — см. `runs/report_sparse.md`.

### H1 — работоспособность: подтверждена

* p = 4 (5 бит), 30 эпох: **7.82 против 8.02** у fp32 → 0.976 (порог 1.1).
* p = 4, 60 эпох: **5.96 против 6.05** → 0.985. Квантование не мешает сходиться.
* Качество почти не зависит от `p` в диапазоне 2…5: даже **p = 2 (8 значений, 3 бита)**
  даёт 7.79 — не хуже fp32. Клип затрагивает 3.4–5.5% весов, сетка не «упирается»
  в предел.

### H2 — эффективность: подтверждена (теоретически)

`p+1` бит на код + 0.5 бита на fp16-масштаб блока из 32 весов:

| p | бит/вес | байт на 826k параметров | против fp32 |
|---|---|---|---|
| 2 | 3.5 | 503 808 | **6.56×** |
| 3 | 4.5 | 602 112 | **5.49×** |
| 4 | 5.5 | 700 416 | **4.72×** |
| 5 | 6.5 | 798 720 | **4.14×** |

Упаковка бит выполнена (`src/pack.py`): реальный `.bin` при p = 4 — **707 183 байта**
против 700 416 теоретических и 3 305 472 у fp32 (**4.67×**), разница с теорией —
только JSON-заголовок. Колонка «.bin, байт» есть теперь в `runs/comparison.md`.

### Квантование эмбеддинга и L1-разреженность (финальный отчёт)

Средняя модель, `quantize_embedding: true` (QuantEmbedding + QuantHead):

| модель | p | ppl | `.bin` | сжатие |
|---|---|---|---|---|
| A fp32 | — | 258.8 | 29 158 216 | 1.00× |
| C, эмбеддинг fp32 | 4 | 254.8 | 18 739 941 | 1.56× |
| C, эмбеддинг fp32 | 7 | 235.4 | 19 919 619 | 1.46× |
| **C + эмбеддинг** | 7 | 241.1 | 7 887 735 | **3.70×** |
| **C + эмбеддинг** | 4 | 239.3 | 5 172 084 | **5.64×** |

Эмбеддинг квантуется без потери качества (0.93× от fp32) и даёт основной выигрыш
в размере: 5.64× против 1.56×. `max|w|` эмбеддинга после QAT 0.342–0.367 — в
`[-1, 1]`, клип 3.2–3.8% (структурный absmax блока).

L1 (`loss = CE + λ·Σ|w|`, вариант B): при p=4 и `λ=2e-5` получается **32% нулей**,
ppl 5.25 (1.094 от fp32 4.80), SZM1-файл **648 968 б** — на **8.2% меньше**
плотной 5-битной C (707 233). При p=7 SZM1 не выигрывает никогда: маска 1 бит
окупается только при f > 50%. Детали — `runs/report_final.md`.

> Инициализация эмбеддинга исправлена (std 0.02 вместо `N(0,1)`): из-за неё
> позиционный сигнал почти терялся. Серии `runs/` обучены до фикса и корректны
> как относительные сравнения, но абсолютные ppl в `runs_l1/` ниже (4.8 против 6.05).

### Ноль: нужен ли он

* В модели **B** (сетка с нулём, 33 значения) после QAT **5.83%** весов ровно нулевые.
* Порог окупаемости вырезания нуля из теории — **f > 17%**; здесь f ≈ 5.8%,
  поэтому 5-битная сетка без нуля выгоднее: 5.00 бита против 5.71 бита
  у варианта с вырезанием (и ppl 7.82 против 7.93).
* В модели **C** нулей **0.000%** — что и требует теория (ноль не входит в сетку,
  округление в 0 сдвигается к ±шагу).

### Кодирование без потерь

`python src/verify_deploy.py runs/C_p4_skipzero`:

```
слоёв: 16, побитово совпало: 16/16, max|ошибка| = 0
справка: если хранить масштаб в fp16 (2 байта/блок), ошибка = 6.1e-05
         (только мантисса масштаба, коды при этом точные)
```

Коды `k -> c` (p+1 бит) и обратное преобразование точны; вес `k·(n/2^p)·scale`
восстанавливается побитово — потому что шаг двоичная дробь и нет 1/3, 1/5 и т.п.

### Наблюдение: масса масштаба (C_p4_global)

Отдельный прогон без per-block масштаба (`n = 1`, шаг 1/16 на все веса) показал
6.55 против 8.02 у fp32 после 30 эпох. Это не ошибка: веса инициализируются
со std = 0.02, квантователь поднимает их до ±1/16 (эффективное усиление ~3×),
и обучение идёт быстрее. Сырые (неквантованные) веса этой же модели дают
perplexity 15.4 — то есть работает именно сетка, а деплой равен `q`.

Важный вывод: на равных 60 эпохах fp32 догоняет (6.05 против 5.96 у C) — то есть
выигрыш квантования здесь в скорости сходимости, а не в предельном качестве.
Поэтому сравнение H1 сделано на двух длительностях.

### Что не сделано (по плану)

* Ноль не вырезается (вариант Б реализован, но упаковка с вырезанием нуля — нет);
  энтропийное кодирование не делалось.
* Квантуются только линейные слои attention/FFN; эмбеддинги, LayerNorm, bias и
  `lm_head` — fp32 (как требует план).
* Один корпус, один seed для основной серии; повторные сиды не гонялись.


## Ограничения этапа

* Биты не упакованы; реальный выигрыш в файле появится после упаковки `p+1` бит.
* Квантуются только линейные слои attention/FFN; `lm_head` и эмбеддинги — fp32.
* Корпус маленький (char-level, ~1 МБ), модель ~0.8 М параметров — этого достаточно
  для сравнения вариантов между собой, но не для выводов о больших LLM.
